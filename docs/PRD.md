# PRD · 个人相册集（Photo Album）

> 项目：`developing` / 塞上空许 — 至静之极
> 版本：v1.0（MVP 范围）　状态：待评审
> 日期：2026-10-08

---

## 1. 背景与目标

当前站点是一份**静态**人像作品集：文案硬编码在 `lib/data.ts`，图片全部引用 Unsplash 外链。
`lib/data.ts` 的文件头已经写明设计意图 ——「将来接 CMS 时，只需把本文件替换为 fetch 实现，组件层无需改动」。

本次迭代把这个意图落地：站点新增一个**可上传、可浏览**的个人相册，图片与元数据存放在**腾讯云 COS**，
不再依赖任何外部图床。

### 1.1 产品目标

| 编号 | 目标 | 衡量方式 |
| --- | --- | --- |
| G1 | 摄影师本人能自助上传照片，无需改代码、无需 SSH | 上传一张照片的端到端操作 ≤ 60 秒 |
| G2 | 访客能在线浏览相册，且首屏加载快 | 相册页 LCP < 2.5s（4G，100 张规模） |
| G3 | 原图永不被前端二次压缩存储，随时可取原片 | 下载原图与上传文件 MD5 一致 |
| G4 | 不破坏现有站点 | 现有 `/` 页面视觉与静态部署链路零改动 |

### 1.2 非目标（MVP 明确不做）

访客上传、多用户与权限体系、EXIF 地理标记、视频/动图支持、AI 人脸聚类、
私密分享链接（带时效 token）、图片水印、多尺寸导出购买、评论与点赞。

## 2. 用户与场景

### 2.1 角色

| 角色 | 身份 | 能做什么 |
| --- | --- | --- |
| **管理员** | 单人，站点所有者（口令登录） | 上传、编辑元数据、删除到回收站、整理相册分组 |
| **访客** | 匿名 | 浏览已发布的相册与照片，查看大图 |

MVP 只做**单管理员**。不做注册、不做多租户。

### 2.2 核心场景

**S1 · 批量导入一段拍摄**
管理员从相机导出一批 JPG → 拖进 `/admin` → 看到每张的进度条 → 全部完成后自动归入「2026 · 秋」相册。
期望：50 张 20MB 以内的照片，总耗时 < 3 分钟，期间可离开页面（单文件失败不阻塞其余）。

**S2 · 补写信息**
上传后补标题、说明、拍摄地点。允许多选批量打标签、批量改相册。

**S3 · 访客浏览**
访客进 `/album` → 看到按时间倒序的相册封面 → 进入某相册 → 网格浏览 → 点击任意一张进灯箱 →
键盘 `←` `→` 翻页、`Esc` 退出 → 可下载原图。

**S4 · 误删恢复**
管理员删错一张 → 从 `/admin` 回收站恢复。

| ID | 需求 |

| F1.3 | 口令只以哈希（bcrypt/scrypt）存于签名服务环境变量，明文不入库不入仓 |
| F1.4 | 连续 5 次失败锁定 15 分钟 |
| F1.5 | 提供退出登录 |

### 3.2 P0 · 上传

| ID | 需求 |
| --- | --- |
| F2.1 | 支持点击选择与拖拽投放；一次可选多个文件 |
| F2.2 | 仅接受 `image/jpeg` `image/png` `image/webp` `image/avif`；单文件 ≤ 50MB |
| F2.3 | **浏览器直传 COS**（预签名 PUT），不经过站点服务器中转 |

| F2.8 | 上传成功后自动写入元数据（标题默认为文件名，可编辑） |

| ID | 需求 |

## 4. 数据模型

单文件 JSON 存放于 COS `_data/album.json`（**私有读**）。

```jsonc
{
  "revision": 42,                    // 乐观锁，每次写入 +1
  "updatedAt": "2026-10-08T02:00:00Z",
  "albums": [
    {
      "id": "alb_shanghai_0317",
      "slug": "shanghai-0317",
      "name": "上海 03:17",
      "desc": "凌晨三点十七分的弄堂",
      "coverKey": "photos/2024/09/01J8...-shanghai-0317.jpg",
      "order": 1
    }
  ],
  "photos": [
    {
      "id": "01J8XXXX",
      "key": "photos/2024/09/01J8XXXX-shanghai-0317.jpg",  // 唯一真相来源
      "albumId": "alb_shanghai_0317",
      "title": "对象 01",
      "caption": "弄堂 · 凌晨",
      "shotAt": "2024-09-22T00:00:00Z",
      "place": "上海 · 静安",
      "tags": ["人像", "夜景"],
      "width": 4000,
      "height": 6000,
      "bytes": 12_400_000,
      "etag": "\"65f1...\"",
      "visible": true,
      "trashedAt": null,
      "createdAt": "2026-10-08T01:20:00Z"
    }
  ]
}
```

**为什么用 JSON 而不是数据库**
这是单人使用的 MVP，读写并发极低。把它放在 COS 里的好处是**没有第二个需要备份的组件**，
且未来想换真实数据库时，前端只依赖 `GET /api/album` 这一个接口，UI 层无需改动。

**升级触发条件**（满足任一即迁走）：照片 > 3000 张、出现第二台写入设备、元数据文件 > 2MB、
需要按任意字段组合查询。

## 5. 关键设计决策

### D1 · 站点保持静态导出，签名能力外挂

现状 `next.config.ts` 设了 `output: "export"`。按 Next 16 官方文档，静态导出**不支持**
「依赖 Request 的 Route Handler」、Server Actions、Cookie、中间件。
也就是说：**上传所需的签名接口无法放进这个 Next 应用里**。

| | 方案 A：静态站 + 独立签名服务 ✅ | 方案 B：Next 全服务端 |
| --- | --- | --- |
| 现有 `output: 'export'` | 保留 | 必须移除 |
| 现有静态部署链路 | 不变 | 作废，需要一台跑 Node 的主机 |
| 服务器成本 | ≈0（云函数按量） | 一台常驻主机 |
| 部署单元 | 2 个 | 1 个 |
| 元数据存储 | COS JSON | COS JSON 或 SQLite |

**选 A。** 理由：现有站点是零服务器成本的静态站且已上线，为一个上传功能把它改成常驻服务不划算；
签名服务本身极轻（单文件、无数据库），放腾讯云 SCF / CloudBase 云函数按量计费几乎为零。

> 关键设计：前端**只依赖 `GET /api/album` 返回的清单**，不关心签名服务是 Node、云函数还是别的实现。
> 将来若要切到方案 B，只换服务端实现，UI 代码零改动。

### D2 · 缩略图不落盘，用数据万象实时处理

数据万象（CI）可以在 URL 上挂参数实时缩放，**不修改原图**：

```
缩略图（网格，限宽 560 等比）
  ?imageMogr2/auto-orient/thumbnail/560x/format/webp/quality/80
预览图（灯箱，限宽 1600 等比）
  ?imageMogr2/auto-orient/thumbnail/1600x/format/webp/quality/85
原图
  无参数
```

> **不要把缩略图强裁成方形。** 网格单元本身按原始宽高比排布，若缩略图裁成 1:1，
> `object-fit: cover` 会二次裁切，观众看到的是被放大的局部（实测过，很难看）。
> 缩略图必须与单元同比例。

好处：省掉一套缩略图生成任务；换封面/改网格尺寸不用重跑批处理。
代价：每次首次访问会实时处理（CI 会缓存结果）。图片量到万级后应改为持久化处理。

### D3 · 原图永久保存，不做前端压缩

摄影作品集的原始文件是资产。所有压缩只发生在**展示层**（URL 参数），
`下载原图` 直出未处理的原文件。

## 6. 验收标准

MVP 算完成，必须全部通过：

1. 在 `/admin` 口令登录后，拖入 20 张混合尺寸照片，全部上传成功且进度条正确。
2. 断网中断一个文件后能单独重试成功，其余文件不受影响。
3. 访客在 `/album` 能看到相册封面；进入相册能浏览全部照片；灯箱键盘翻页与退出正常。
4. 手机视口（375×667）下网格与灯箱均无横向滚动条。
5. 缩略图请求的 URL 带 `imageMogr2` 参数，返回图片宽度确为 320px 且为 webp。
6. 打开「下载原图」，下载文件 MD5 与上传源文件一致。
7. 删除一张照片后，访客侧不再出现；回收站可恢复，恢复后访客侧重新可见。
8. 移动端首屏 LCP < 2.5s（Chrome DevTools 4G 节流，100 张相册）。
9. `npm run build` 通过；`out/album/index.html` 与 `out/admin/index.html` 已生成。
10. 全站源码与产物中检索不到 `SecretKey` 字面量。

## 7. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 桶 CORS 配错 → 上传静默失败 | 阻塞 | 上线前用 `curl -X OPTIONS` 验证；`Expose-Headers` 必须含 `ETag` |
| 2024-01-01 后创建的桶不支持默认域名直接预览文件 | 部分环境图裂 | 尽早绑定自定义域名 + 开 CDN |
| `album.json` 并发写覆盖 | 丢元数据 | `revision` 乐观锁 + 单管理员约束 |
| 数据万象未开通 → 缩略图 404 | 阻塞浏览 | M0 阶段就开通并验证 |
| 签名服务被刷 | 费用失控 | 预签名短有效期（600s）+ 单 IP 限流 + 密钥最小权限 |
| 本机 npm 缓存无写权限（`EPERM unlink _cacache/tmp`） | 阻塞安装依赖 | 在自有终端执行安装，或 `npm i --cache /tmp/npm-cache` |
